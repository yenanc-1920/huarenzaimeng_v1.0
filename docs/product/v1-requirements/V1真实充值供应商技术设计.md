- 《小啦全球充 API 接口 v5.0》：签名、充值提交、原单查询、回调、余额、国家、产品、类型、运营商识别接口。
- 《小啦全球充操作手册》：余额、产品折扣、API 订单、余额变动和失败退款等后台事实。

### 1.2 已核验现场事实

- 当前供应商账户余额为 0，订单为 0。
- 已存在 32 位 API Key；本文不读取、不复制、不回传该值。

## 2. 设计目标与硬约束

### 2.1 目标

1. 让现有报价—订单—微信支付—充值—结果展示形成真实可审计闭环，完整覆盖平台定义的余额、流量、套餐三类商品。
2. 将供应商协议隔离在适配器内，领域层只消费统一商品、统一金额和统一充值状态。
3. 通过“单次提交闩锁 + 原单查询 + 幂等回调”避免重复充值。
4. 让 A130 控制目录映射、价格和启停，A140 展示订单/充值事实，A110 处理冲突与未知态。
5. 在无沙箱条件下，先用 Fake 和只读真实接口验证，再逐运营商进行人工批准的小额真充。

### 2.2 不可突破的硬约束

- **不自动换渠道**：WINLA 故障或余额不足时停止新提交，不把既有订单切到其他供应商。
- **不自动重充**：无论超时、断线、重启还是返回未知，都不得再次调用充值提交接口。
- **UNKNOWN 不自动退款**：只允许查询同一 `user_order_no` 的原单；确认失败后才进入既有退款决策流程。
- **历史订单不漂移**：订单固定供应商、供应商 SKU、目录批次、价格版本、汇率版本和报价快照。
- **支付先于充值**：只有微信支付权威事实为成功、订单仍满足约束时，才可争抢一次充值提交权。
- **供应商返回“已受理”不是成功**：必须等待原单查询或已验签回调给出终态。
- 禁止把 API Key、签名、完整手机号、原始请求/响应或数据库凭据写入日志、证据或前端 DTO。

## 3. 总体架构

```text
小程序 -> Buyer API -> Quote/Order/WeChat Payment facts
                           |
                           v（支付成功且单次闩锁获胜）
                    Topup Orchestrator
                    /      |       \
          Catalog Port  Topup Port  Balance Port
                    \      |       /
                       WINLA Adapter
                           |
                    WINLA HTTPS API

WINLA callback -> Public Callback Endpoint -> Receipt Store -> State Reducer
定时/人工查询 --------------------------------> Original Order Query
                                                   |
                           A140 状态 <--- Topup Projection ---> A110 交易差异
                           A130 商品 <--- Catalog Normalize/Review/Publish
```

供应商适配器不得直接更新买家订单、发起退款或发布商品。它只产生不可变的供应商观察事实；领域状态归并器负责按单调规则投影。

## 4. 供应商抽象端口与 WINLA 适配器

### 4.1 领域端口

| 端口 | 最小职责 | 禁止行为 |
|---|---|---|
| `SupplierCatalogPort` | 拉取国家、类型、产品并返回原始快照 | 不直接上架、不自行修正供应商字段 |
| `SupplierOperatorDetectionPort` | 对规范化手机号执行一次识别并返回候选及置信边界 | 不声称 100% 准确、不替代用户手选 |
| `SupplierTopupPort` | `submitOnce` 与 `queryOriginal` | 不内置自动重试、换渠道、退款 |
| `SupplierCallbackVerifier` | 规范化参数、重算签名、输出已验证回调事实 | 不接受未验签回调作为终态 |
| `SupplierBalancePort` | 只读余额及币种/单位 | 不执行充值供应商账户等资金操作 |
| `SupplierCapabilityPort` | 返回支持国家、运营商、商品类型和启用状态 | 不把后台品牌/分销功能暴露给 V1 |

所有端口 DTO 使用平台类型（`Money`、`NormalizedProductKind`、`TopupObservation`），不得让 `state=1/2/3`、`status=200/201/202` 或签名字段穿透到领域和前端。

### 4.2 WINLA 传输规则

- 仅允许固定 HTTPS 主机和精确路径；禁止跟随跨主机重定向。
- 业务调用优先使用 POST + `application/x-www-form-urlencoded`，响应按 UTF-8 JSON 解析；即使手册允许 GET，也不在 URL 中携带业务参数。
- 连接、读取、总时限分别配置；充值提交**网络层重试次数固定为 0**。
- 签名：移除 `sign`，排除空值，按参数名 ASCII 升序拼接 `key=value&...`，末尾追加供应商 Key 后计算 32 位 MD5。所有值按供应商 UTF-8 编码规则处理。签名算法只存在于 `WinlaSigner`。
- `uid`、Key、端点、白名单环境身份由受控配置注入；Key 不入数据库。
- 供应商业务码与 HTTP 状态分别保存为枚举/脱敏事实。未知业务码一律失败关闭并转人工，不猜测语义。

### 4.3 `user_order_no`

- 创建充值意图时生成一次，之后永不更换；格式建议为 `W` + 31 位大写 Base32/十六进制派生值，总长不超过 32，仅字母数字。
- 数据库全局唯一；同一订单目的（`order_id + TOPUP`）也唯一。
- 发生超时、断线或进程退出时，仍使用该编号查询原单，绝不重新生成编号后提交。

## 5. 商品目录、归一化与 A130

### 5.1 批次链路

1. `FETCHED`：拉取国家、类型、产品，保存不可变原始响应摘要及逐商品原始快照。
2. `VALIDATED` / `PARTIAL` / `REJECTED`：验证孟加拉、五运营商、金额/币种/单位、标题、有效期、可用性和重复 SKU。
3. `MAPPED`：人工确认运营商别名、平台商品类型和规格字段。
4. `PRICED`：关联平台价格版本；供应商成本变化不会反写历史报价。
5. `PUBLISHED`：仅 `SUPER_ADMIN` 可在 A130 对已通过映射与价格检查的 SKU 启用。

新批次不覆盖旧批次。供应商删除或下架 SKU 时，新报价停止使用；历史订单仍指向原批次和原始快照。

### 5.2 类型归一化

| 供应商原始信息 | 平台类型 | 处理 |
|---|---|---|
| 话费 | `BALANCE` | 面值型；金额和到账面值分别保存 |
| 流量，只有数据量 | `DATA` | 解析数据量、单位、有效期 |
| 流量，但标题/描述含分钟或短信 | `BUNDLE` | 解析数据、分钟、短信及有效期 |
| 信息矛盾、无法解析或有效期无效 | `QUARANTINED` | 禁止报价与启用，A130 人工处理 |

归一化必须记录 `normalization_rule_version` 和人工覆盖者。不能根据“流量”原始类型直接断言它不是套餐。

### 5.3 A130 必须可见/可操作

- 目录批次、抓取时间、原始 SKU、运营商原值/映射值、原始类型/平台类型、原价 `yj`、折扣价 `yh`、有效期原文、解析结果、质量告警、价格版本和启用状态。
- `CONTENT_OPERATOR` 仅可维护/预览用户可见的展示文案，不可改变供应商 SKU 映射、运营商映射、商品类型、成本/售价、渠道或启用状态。
- 真实目录同步确认、映射、平台售价/利润规则、渠道配置、SKU/运营商启停均仅限 `SUPER_ADMIN`；价格或映射写动作不得通过内容角色间接触发。
- 其他后台角色只能按既有权限查看，不得启用真实渠道。
- 批量启用必须逐 SKU 通过同一校验；不能用供应商“全部商品”直接发布。

## 6. 定价与报价快照

- `yj`、`yh`、提交/查询中的 `price` 与回调 `order_money` 的单位和币种必须由供应商书面确认。在确认前，不以字段名或样本折扣推断“分/元”“BDT/CNY”。
- 样本 15%/3% 仅用于异常探测，不作为固定折扣。
- 平台成本输入使用供应商明确的实际成本字段；平台售价由 A130 价格版本决定，并沿用既有汇率、舍入和利润规则。
- 买家报价必须固化：`supplier_code`、`supplier_product_code`、`catalog_batch_id`、`supplier_cost_snapshot`、`supplier_cost_currency`、`fx_rate_version`、`platform_price`、`payment_amount`、`price_version`、`expires_at`，以及用户下单时实际看见的商品名称、运营商、余额/流量/分钟/短信权益、有效期、适用条件和限制文案。历史订单详情只能读该快照，不能读当前目录拼装。
- 所有供应商金额事实同时保存：原始字段名、原始字符串、原单位、原币种、`money_contract_version`、规范化 minor units、规范化状态（`CONFIRMED/UNCONFIRMED/INVALID`）和规范化失败原因。字段单位/币种契约未获书面确认时状态必须为 `UNCONFIRMED`，禁止真实提交、成本核算和自动对账。
- 支付和充值均按订单快照执行；目录刷新、成本或汇率变化不得修改已创建订单。
- 提交前若供应商实际扣款口径与快照不一致，停止提交并进入 `PRICE_MISMATCH` 人工处理，不即时改价。

## 7. 订单、充值意图与单次提交闩锁

### 7.1 提交前置条件

只有以下条件同时满足才可创建/消费充值意图：

1. 订单、买家、手机号、运营商与报价快照一致，订单未取消/退款。
2. 微信支付权威事实为成功，支付金额与订单一致且未被消费过。
3. 历史订单绑定的 WINLA 渠道与 SKU 仍满足执行约束；不得临时换 SKU。
4. WINLA 渠道、该运营商和 SKU 处于可提交状态，目录未过期。
5. 余额读取成功并达到配置的安全阈值；余额未知或当前为 0 时禁止提交。
6. 回调可达性、查询能力和告警处于上线门禁允许状态。
7. 以供应商币种 minor units 对可用余额执行跨订单原子预占成功；`available = confirmed_balance - active_reservations - safety_buffer`。预占与 `TopupIntent` 同事务绑定，提交前不可重复占用，只有确认失败/受控取消或对账完成后按确定规则释放。
8. 该渠道的全局并发、运营商并发和账户在途金额均未超过配置上限；限制器必须跨实例生效，不能依赖单 JVM 计数。

### 7.2 闩锁时序

```text
支付成功事实
  -> 创建唯一 TopupIntent + 固定 user_order_no
  -> 同事务 CAS：CREATED -> SUBMITTING，并插入唯一 SubmitLatch
  -> 事务提交后调用 WINLA submit（不重试）
  -> 保存 submit observation
  -> 已受理：SUBMITTED_NON_TERMINAL
  -> 超时/断线/解析失败：UNKNOWN
  -> 后续只能 queryOriginal(user_order_no)
```

并发请求、消息重复、容器重启和人工点击都只能有一个调用者赢得 `SubmitLatch`。闩锁存在即禁止再次提交；失败删除闩锁、重置状态或生成新商户单号均被禁止。

余额预占不是供应商真实余额保证，也不是资金扣款。提交受理后预占转为在途占用；只有供应商终态和余额/账单对账能使其结清。UNKNOWN 期间必须继续占用，禁止因本地超时释放后让其他订单超卖供应商余额。

## 8. 内部状态机与供应商状态映射

### 8.1 内部状态

`CREATED -> SUBMITTING -> SUBMITTED_NON_TERMINAL | UNKNOWN -> PROCESSING -> SUCCEEDED | FAILED`

旁路状态：

- `RECONCILIATION_REQUIRED`：终态冲突、金额/SKU/号码摘要不一致、无法解释的供应商码。
- `DISABLED_BEFORE_SUBMIT`：尚未提交且渠道被停用。
- `REFUND_REVIEW`：只有确认 `FAILED` 后，交给既有退款策略人工/受控处理；不是充值状态自动动作。

### 8.2 映射表

| 来源 | 供应商值 | 内部观察 | 规则 |
|---|---:|---|---|
| 提交响应 | 受理/返回订单号 | `SUBMITTED_NON_TERMINAL` | 不展示为充值成功 |
| 原单查询 | 1 | `PROCESSING` | 继续限频查询 |
| 原单查询 | 2 | `SUCCEEDED` | 可形成权威成功事实 |
| 原单查询 | 3 | `FAILED` | 可形成权威失败事实 |
| 回调 | 201 | `PROCESSING` | 必须先验签 |
| 回调 | 200 | `SUCCEEDED` | 必须先验签且身份/金额匹配 |
| 回调 | 202 | `FAILED` | 必须先验签且身份/金额匹配 |
| 网络/超时/解析异常 | — | `UNKNOWN` | 只查原单，禁止重充/退款 |
| 未知码或终态冲突 | 其他 | `RECONCILIATION_REQUIRED` | A110 人工核验 |

状态归并必须单调：终态后的迟到 `PROCESSING` 只记审计、不回退；重复同终态幂等；成功与失败冲突不互相覆盖，而是进入 A110。原单查询与已验签回调的最终权威优先级、冲突处理必须以供应商书面规则冻结。

### 8.3 UNKNOWN 查询任务

- 每个充值意图至多存在一个活动 `OriginalOrderQueryTask`，数据库唯一约束为 `(topup_intent_id, task_kind)`；调度器抢占需带租约/CAS，防止多实例重复查询。
- 查询只使用同一 `user_order_no`，不调用充值提交。查询失败允许按配置预算退避：初始间隔、倍率、最大间隔、最大次数、最长观察窗均须版本化；普通 HTTP/网络重试不得绕开该预算。
- 达到最大次数或最长观察窗仍无终态时停止自动查询，保持 `UNKNOWN/REVIEW_REQUIRED`、保留余额占用并进入 A110；不自动重充、不自动退款。
- 供应商书面确认查询保留期和建议频率后才能冻结生产预算；当前设计不预设具体秒数和次数。

## 9. 回调安全、幂等、乱序与迟到

- 固定公开路径建议为 `POST /supplier-callback/v1/winla/topup`，仅接受表单编码、限定请求大小/字段集合和 UTF-8。
- 必须按供应商规则重算并恒定时间比较签名。手册若允许“不验签”，平台仍不得接受未验签回调作为终态；在供应商无法保证签名时，回调仅作为“立即查询原单”的提示。供应商 MD5 参数签名没有时间戳/nonce 新鲜度保证，平台不能据此宣称防重放；安全目标是让相同或重放载荷命中幂等收件约束，产生零新增副作用。
- 回调先持久化不可变 `CallbackReceipt`，再异步/事务内归并状态。唯一事件摘要由供应商、供应商订单号、商户订单号、状态、金额、PIN/序列摘要及规范化载荷摘要构成。
- 重复回调命中唯一约束后返回同一确认结果，不重复执行业务动作。
- 迟到/乱序按第 8 节单调规则处理；终态冲突、金额不符、未知订单、签名失败均不更新订单，保留脱敏证据并进入告警/对账。
- 回调或原单查询只能核验供应商实际返回且书面定义的字段，例如 `user_order_no`、供应商订单号、状态和金额。若协议未返回手机号、供应商 SKU 或产品权益，不得写成“已核验手机号/SKU”；这些只能依赖提交前内部快照与 `user_order_no` 关联，并将缺失的外部交叉核验标记为契约限制。
- 回调成功应答的 HTTP 状态与响应正文、供应商重试周期和源 IP 范围尚待书面确认；未确认前不能开放真实充值。

## 10. 数据模型与唯一约束

下表为最小新增/扩展模型；字段名可按现有命名规范调整，但语义与约束不得弱化。

| 模型 | 核心字段 | 必须约束 |
|---|---|---|
| `supplier_channel` | code、capability、status、config_version | `code` 唯一；Key 不入表 |
| `supplier_catalog_batch` | supplier、fetched_at、raw_digest、state | `(supplier, raw_digest)` 唯一 |
| `supplier_product_raw` | batch、external_id、raw_type、title、raw_price、raw_validity、payload_digest | `(batch, external_id)` 唯一；原始快照不可变 |
| `supplier_product_mapping` | external_id、operator、normalized_kind、rule_version、review_state | `(supplier, external_id, mapping_version)` 唯一 |
| `supplier_product_activation` | mapping_version、price_version、enabled、operator | 仅已审核映射可启用 |
| `operator_detection_attempt` | phone_hmac、result、latency、cost、manual_override | 不存明文手机号；请求键幂等 |
| `topup_intent` | order_id、payment_fact_id、supplier、SKU 快照、`user_order_no`、state | `order_id` 唯一；`user_order_no` 全局唯一 |
| `topup_submit_latch` | intent_id、claimed_at、request_digest | `intent_id` 唯一；只增不删 |
| `supplier_balance_reservation` | intent、currency、minor_units、state、expires_policy | `intent_id` 唯一；余额/预占更新需锁或原子版本 CAS |
| `supplier_topup_observation` | intent、source、external_order_no、state、amount、observed_at、digest | `(supplier, digest)` 唯一；追加式 |
| `supplier_callback_receipt` | headers 摘要、payload 摘要、signature_valid、received_at | `(supplier, event_digest)` 唯一 |
| `supplier_balance_snapshot` | balance、currency、observed_at、result | 只读追加式 |
| `original_order_query_task` | intent、attempt_count、next_at、deadline、lease、state | `(intent_id, task_kind)` 唯一；预算和退避版本化 |
| `topup_reconciliation_case` | intent、reason、evidence refs、resolution | 一个开放原因仅一个活动案例 |

手机号在订单既有受控字段中保存；供应商相关新表只保存掩码或 HMAC。供应商原始载荷如确需审计，应加密、最短保留期、限制访问，并与普通应用日志隔离。

数据库迁移只允许新增版本脚本；不得修改既有 V1–V12。正式版本号由实现阶段在当前迁移头之后顺序分配。

## 11. API 与 DTO

### 11.1 买家 API

| API | 用途 | 关键返回/约束 |
|---|---|---|
| `POST /buyer-api/v1/operators/detect` | 可选运营商识别 | 返回候选、`manualSelectionRequired`、过期时间；不返回供应商成本 |
| 既有目录/报价 API | 返回已启用平台商品与报价 | 只用平台类型、价格和运营商；不暴露 WINLA SKU 以外部可控方式提交 |
| 既有订单创建/支付 API | 固化报价及支付 | 客户端不能指定供应商、成本或回调状态 |
| `GET /buyer-api/v1/orders/{id}/topup` | 查询充值进度 | `PENDING/PROCESSING/SUCCEEDED/FAILED/REVIEW_REQUIRED`，UNKNOWN 对用户显示“处理中，请勿重复支付” |

运营商识别超时、低置信或错误时必须允许用户手选；下单时服务端校验手机号、所选运营商和商品的兼容性。

### 11.2 后台 API

- A130：目录批次列表/详情、同步命令、质量问题、类型/运营商映射、价格版本、SKU/运营商启停、余额只读。
- A140：订单、支付、充值意图、供应商订单、当前投影、全部观察时间线；不得提供“再次充值”按钮。
- A110 是统一“交易差异”入口：支付、订单、报价/权益快照、充值提交、供应商终态、退款和供应商余额/扣款的任一差异都在同一案例模型中归集；终态冲突、UNKNOWN 超窗、金额/SKU 关联不一致、无对应回调、余额扣减不一致只是原因枚举。只允许受控裁定，不允许编辑供应商原始事实。
- A100 客服只能查看脱敏订单、支付、充值时间线和 A110 案例公开结论，按既有授权发起客服备注/升级；不得提交或重提充值、修改状态、映射、价格、退款事实。
- A130 权限必须在 API 层再次强制：`CONTENT_OPERATOR` 仅展示文案；真实映射、价格、渠道、启用仅 `SUPER_ADMIN`。
- 所有写命令带请求幂等键、操作者、理由和版本号；启用真实 SKU/运营商仅 `SUPER_ADMIN`。

### 11.3 前台页面状态投影

- P014（充值进度链路）展示订单固化的余额/流量/套餐权益、有效期与限制；`UNKNOWN` 展示“充值处理中，请勿重复操作或充值”；提交后不可因目录变化改写。
- P015（充值异常/失败/退款复核链路）展示确定失败、退款复核与退款进度，并提供客服入口；退款未形成权威事实前不得展示“已退款”。
- P021（订单详情/进度链路）展示支付、充值、退款三个独立状态及时间线：UNKNOWN/超窗显示处理中或待人工核验；失败、退款申请、退款处理中、退款成功/失败均来自各自事实投影，不用充值失败推导退款成功。
- A100 使用同一投影的脱敏客服视图；A110 使用包含原始差异引用的审计视图。前后台不得各自翻译出冲突状态。

### 11.4 供应商回调 API

回调 DTO 与领域 DTO 分离。控制器只完成传输校验、载荷规范化、收件入库和快速确认；状态归并由应用服务执行，防止供应商超时导致重复回调放大。

## 12. Secret、IP 与 CloudBase

### 12.1 Secret

- API Key、`uid`（若供应商视为凭据）、微信支付密钥均由 CloudBase 受控 Secret 注入，不进 Git、镜像、数据库、启动参数或普通环境导出。
- 启动时只验证存在性/格式和 Secret 版本引用，禁止打印值。轮换需支持旧/新回调签名短暂并行的明确窗口，不能无限双 Key。
- 本次已知 Key 的“32 位存在性”不等于可用性或授权，不得为测试读取其内容。
- 出站调用身份与回调验签身份必须使用不同的运行身份和最小 Secret 访问策略：出站适配器可读调用所需凭据但不能改回调配置；回调服务只读验签所需版本，不获得供应商出站调用权限。即使供应商暂时共用同一 Key，也要以两个独立 Secret 引用/访问主体隔离并记录轮换关联，禁止让公网回调进程成为可发起充值的身份。

### 12.2 固定出口与 IP 白名单

- WINLA 要求 IP 白名单。CloudBase 服务必须具备已验证的固定公网出口；若平台本身不保证固定出口，应通过受控 NAT/网关形成唯一出口。
- 上线证据必须包含：环境、服务、出口 IP 引用、供应商白名单生效时间和一次只读接口成功结果。不可把临时构建机、个人电脑 IP 加入正式白名单。
- 出口不确定时目录、余额和充值调用全部失败关闭；不能以放宽白名单替代固定出口。

### 12.3 回调入口

- 使用已绑定的 CloudBase HTTPS 自定义域名，配置精确回调路径，不与后台 Cookie 登录或迁移关闭态过滤器冲突。
- 回调地址当前未配置，是 P0；配置后需验证 DNS/TLS、路由、请求大小、表单解析、签名、限流、重复回调和 2xx 应答。
- 反向代理必须保留签名所需的原始字段语义；任何转码或空值丢弃规则需纳入契约测试。

### 12.4 手机号外发与隐私

- 真实充值和可选运营商识别会把手机号发送给境外/外部供应商。首次使用前必须向用户明确告知接收方类别、处理目的（识别运营商/履行充值）、字段、可能的地域、保留期和退出/人工手选方式，并取得适用法律要求下的同意或其他合法基础。
- 目的限制：手机号仅用于当前订单履约或用户主动触发的识别，禁止用于营销、画像、供应商分销或与充值无关的复用；运营商识别不可静默预调用。
- 与供应商合同/数据处理附件必须冻结：子处理方、传输地域、安全措施、保留/删除期限、用户删除/查询协助、事件通知、合同终止后的删除证明。供应商不能书面满足时不得开放真实调用。
- V1 订单受控字段中的充值手机号按已冻结策略明文保存，以支持实际充值、原单查询、退款和争议处理；用户端与普通后台默认脱敏，日志、事件、错误响应禁止完整号码。KMS/字段级密文属于后续版本。原始供应商请求/响应仍按最短必要期隔离并严格限权；业务保留期届满后删除或不可逆脱敏。删除不能破坏法定账务/争议证据，但需对保留字段、目的和期限分层记录。

## 13. 日志、监控、余额与对账

### 13.1 日志脱敏

允许记录：内部订单/意图 ID、供应商代号、阶段、状态枚举、业务码、延迟、重试计数（查询）、载荷摘要、异常类名。
禁止记录：Key、`sign`、完整手机号、完整 PIN/序列、请求/响应全文、数据库连接、微信身份、供应商后台截图中的敏感值。

### 13.2 指标与告警

- 提交计数、受理率、终态成功/失败率、UNKNOWN 数量和年龄、回调验签失败/重复/迟到/冲突、查询延迟、目录陈旧、隔离 SKU 数、余额及扣减差异。
- 当前余额 0：真实提交必须硬阻断并告警。
- 告警阈值、余额币种和安全余量由运营/财务配置，技术设计不凭样本金额代定。

### 13.3 对账

- 按内部订单、`user_order_no`、供应商订单号、供应商扣款、回调/查询终态、微信收款和退款事实进行日对账。
- 供应商后台“API 扣款/失败退款”只作为外部账务事实；失败退款到供应商余额不等于已向买家退款。
- UNKNOWN、终态冲突、金额不符、成功无扣款/扣款无订单进入 A110；不自动重充、不自动退款。

## 14. 测试与真实小额验证矩阵

### 14.1 本地 Fake（不接外部）

- 签名排序、空值、编码、大小写和常量时间比较。
- 目录批次重复、SKU 删除、五运营商映射、话费/流量/组合套餐、无效有效期、价格单位异常。
- 同订单并发 2–100 次仅一次 `submit`；超时、断线、进程退出后仅查询原单。
- 跨订单并发争抢余额时原子预占不得超卖；跨实例通道并发上限生效；UNKNOWN 保持占用，确定终态按规则结清。
- 查询 1/2/3，回调 200/201/202，重复、乱序、迟到、未知订单、错签、金额不符、成功/失败冲突。
- UNKNOWN 查询唯一任务、退避、最大次数/最长窗和租约接管；预算耗尽后进入 A110 且不产生第二次提交。
- 回调重放（MD5 正确但无新鲜度）只能形成一个收件事实和零重复业务副作用；只验证协议实际返回字段。
- 余额 0/未知/不足阻断；渠道/SKU 停用只阻止新提交，不破坏历史查询/回调。
- A130 权限、A140 只读状态、A110 交易差异闭环及日志无 Secret/手机号。

### 14.2 真实只读验证

- 固定身份下调用余额、国家、类型、孟加拉产品目录，保存脱敏摘要与批次；不创建订单。
- 运营商识别是收费调用，不归入普通只读巡检；需单独批准测试号码、次数和成本后执行。
- 校验五运营商、类型/产品字段、币种/单位、目录更新和错误码，发现异常只隔离，不自动修数据。

### 14.3 人工小额真充（无沙箱）

每个案例必须有一次性批准、真实且获同意的测试手机号、明确供应商 SKU/金额、订单号、操作者和观察窗口。先从一个运营商的最小安全话费商品开始；单次提交、失败不重试。通过提交、查询、回调、到账和对账后，才扩至数据/套餐，再逐步覆盖 Airtel、Banglalink、Grameenphone、Robi、Teletalk。任何一例 UNKNOWN 或对账不符即停止扩容。

## 15. 灰度、停用与故障策略

### 15.1 灰度顺序

1. `DISABLED`：只完成 Fake；外部调用全关。
2. `CATALOG_READ_ONLY`：余额/目录只读，商品不售卖。
3. `ONE_OPERATOR_AIRTIME`：一个运营商、一个小额话费 SKU、内部白名单买家。
4. `ONE_OPERATOR_DATA_BUNDLE`：同运营商扩展流量/套餐。
5. `MULTI_OPERATOR_LIMITED`：逐一加入其余运营商，每次复用相同验收矩阵。
6. `V1_ENABLED`：仅已审核 SKU 面向 V1 用户；仍保留逐运营商/类型熔断。

### 15.2 停用与故障

- 余额不足/未知、签名或白名单错误、目录陈旧、回调大面积失败、UNKNOWN 超阈值、供应商维护时，立即停用**新报价/新提交**。
- 已支付未提交订单进入人工受控处理；不得悄悄换渠道或商品。
- 已提交订单继续接受回调并查询原单；停用不能切断收尾能力。
- 恢复前需要只读健康、余额、目录、回调和一笔受控案例通过；禁止自动恢复全量。

## 16. P0/P1 与上线门禁

### 16.1 P0（6 项，未关闭前 NO-GO 真实充值）

| ID | 问题 | 最小关闭条件 |
|---|---|---|
| WINLA-P0-01 | 余额为 0、商务/真实充值资格未证实 | 受控入金完成，币种/余额单位/扣款退款规则确认，余额门禁通过 |
| WINLA-P0-02 | 回调地址未配置，验签及应答契约不完整 | 配置 CloudBase HTTPS 精确回调；供应商书面确认签名、应答、重试、源 IP；重复/乱序测试通过 |
| WINLA-P0-03 | CloudBase 固定出口与供应商 IP 白名单未形成证据 | 固定出口身份、白名单生效和只读接口实测全部匹配 |
| WINLA-P0-04 | 金额单位/币种、字段权威性和终态冲突规则存在手册歧义 | 供应商书面确认第 17 节关键项；冻结带版本的 raw→minor units 契约与适配器样例，所有金额状态为 `CONFIRMED` |
| WINLA-P0-05 | 无沙箱，尚无受控真充闭环证据 | Fake 全矩阵、真实只读、一次人工批准的小额真充及到账/回调/对账完成 |
| WINLA-P0-06 | 手机号外发与供应商数据处理闭环未关闭 | 完成 §12.4 用户告知与合法基础、取得 §17.15 书面数据处理条款，并以真实号码完成最小化验证 |

### 16.2 P1（4 项，可开发但必须在相应灰度前关闭）

| ID | 问题 | 最小调整 |
|---|---|---|
| WINLA-P1-01 | 目录含无效有效期、组合套餐和别名质量异常 | 批次/隔离/人工映射与规则版本上线，异常 SKU 默认禁用 |
| WINLA-P1-02 | 运营商识别收费且非 100% 准确 | 5 秒时限、次数预算、人工手选和下单二次校验 |
| WINLA-P1-03 | MD5 为供应商既定弱签名机制且无新鲜度 | 仅 HTTPS、Key/运行身份隔离、固定出口、严格规范化、回调签名和轮换；以收件唯一约束保证重放无副作用，不自创协议字段 |
| WINLA-P1-04 | 余额、并发、UNKNOWN、回调和对账阈值未定 | 在 A130/A110 配置并演练余额原子预占、通道并发、查询预算/退避/最长窗、告警、熔断和人工恢复 |

### 16.3 GO 判据

技术实现可以按本文进入开发，故为 `CONDITIONAL_GO`；真实充值上线必须同时满足：P0=0、目标运营商对应 P1=0、代码门禁与回归通过、固定制品/环境/Secret/出口/回调身份一致、一次性真充授权有效。普通 Fake、构建成功、余额查询成功或供应商“受理”均不等于真实充值 PASS。

## 17. 必须由供应商书面确认的事项

1. 签约主体、产品名称、API v5.0 的正式版本和全部正式 HTTPS 域名/路径。
2. `uid`/Key 的权限、轮换、失效、测试与生产隔离方式；IP 白名单数量、IPv4/IPv6 和生效时间。
3. 签名精确算法：空值、URL 编码、中文、大小写、数值格式；回调是否每次必带有效签名。
4. 回调确认需要的 HTTP 状态/正文、超时、重试间隔/次数、源 IP 范围以及迟到上限。
5. `yj`、`yh`、提交/查询 `price`、回调 `order_money`、余额字段的单位、币种、精度与舍入。
6. 提交响应“受理”的精确语义；重复 `user_order_no` 的返回、幂等保证、订单保存和可查询期限。
7. 查询接口 `user_order_no` 是否实际必填（手册标记存在歧义）；查询 1/2/3 与回调 200/201/202 的权威关系和终态冲突处理。
8. `recharge_no` 对话费、流量、组合套餐是否均必填，以及孟加拉号码格式/国家码规则。
9. 产品代码稳定性、目录刷新频率、下架/价格变化通知、国家/类型/运营商字段枚举和五运营商别名。
10. 数据、分钟、短信、有效期的结构化字段或可靠解析规则；“无效有效期”等异常的修复责任。
11. 余额扣减时点、失败返还时点、对账单获取方式、低余额告警和账务争议流程。
12. 限流、并发、维护窗口、SLA、超时建议、故障联系和生产变更通知。
13. 无沙箱的正式确认、真实小额测试政策、允许的测试 SKU/号码及失败款项处理。
14. 运营商识别计费、可用国家、错误率/置信字段、缓存许可、号码隐私与保留政策。
