- `CloudBase` 仅在现有工具、服务标识、接口字段或证据原文中保留；引用时须明确它属于本项目微信云托管的控制面或发布链语境，不代表项目运行在另一平台。

## 试运行晋级策略

1. DEV：跑通全部 V1 功能和真实外部链路，允许使用明确标识的最小测试数据与受控小额资金。
2. TEST：验证同一候选的环境隔离、数据库迁移、配置完整性和关键回归。
3. STAGE：按生产等价配置完成上线演练、回滚、监控、告警和运营接管检查。
4. PROD：仅在南哥明确授权后发布；先小范围试运行，观察稳定后再扩大。

阶段之间禁止顺手夹带新功能。阻断缺陷做一次有界修复并定向验证，再生成新的冻结候选；非阻断事项进入试运行观察台账。

## DEV 发布链

1. 代码进入 `dev`。
2. GitHub `full-release-gate` 执行完整确定性门禁。
3. Buildx 构建精确 `${{ github.sha }}` DEV 镜像。
4. 成功后才推进 `deploy/dev`。
5. 微信云托管通过现有 `CloudBase` 控制面链路监听部署分支并创建新版本。
6. 控制台版本、实例身份和健康探针共同证明部署，不以单独 200/UP 代替版本证据。

## 运维规则

- 发布成功不等于服务就绪；等待迁移、实例健康和目标版本确认。
- 若 Flyway 在 `ParsingContext.populate` 以 `currentSchema=null` 失败且尚无迁移 SQL 日志，先核对自定义 Flyway Bean 的 `defaultSchema` 绑定；不得误判为数据库连接失败或执行 repair。
- 环境变量保存通常需新版本才生效；验证时记录服务、版本、实例和时间。
- 不自动重发失败部署；先读取首个稳定失败步骤。
- 不在运维文档或截图中保存秘密值。
- PROD 发布、密钥变更和真实迁移必须由南哥确认。

## 新电脑迁移

- 换机统一执行`docs/deployment/NEW-COMPUTER-MIGRATION-PLAN.md`，任务ID为`PC-MIGRATION-01`。
- Git只负责恢复已提交内容；未提交／未跟踪内容和被Git忽略的项目来源资料必须进入经脱敏、验哈希的加密迁移包。
- 外部账号在新电脑重新认证，不复制浏览器Cookie、Codex内部数据库、微信开发者工具登录缓存或整个用户配置目录。
- `.m2-local`、`node_modules`、构建产物、临时目录、历史RunId和隔离运行时缓存不迁移；环境治理运行时必须从官方来源按固定清单重新下载和验哈希。
- 新电脑验证按Git身份→基线检查→环境治理无残留探针→定向构建→完整DEV门禁→外部只读核验递进，任何低等级结果不得外推为微信云托管、真实数据库、业务或生产PASS。
