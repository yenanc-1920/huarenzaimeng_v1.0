# 治理、权限与变更规则

## 优先级

1. 南哥明确指令与授权。
2. 本目录中的已批准执行基线。
3. 已记录且未被替代的批准决定。
4. 角色职责。
5. 来源、历史记录、草稿和建议。

## 基本原则

- 证据优先、最小必要变更、职责分离、失败关闭、可追溯。
- 事实、约束、假设、建议、决策、风险和问题必须明确区分。
- 不得把发布成功等同服务就绪，不得把门禁 GO 等同真实业务 PASS。
- 每个问题按“定位→一次有界修复→定向验证→提交→允许时推送合并”处理。
- 同一首因连续三轮没有新增证据时停止改代码，转环境或外部支持问题。

## 授权边界

角色可在批准范围内自主执行只读检查、代码修改、定向测试、功能分支提交与推送。以下事项必须暂停并请南哥确认：

- 真实资金或真实供应商扣款；
- 生产发布或正式小程序发布；
- 密钥、证书、权限和长期凭据变更；
- 数据库破坏性操作、真实迁移或不可逆清理；
- 产品范围、商业规则、法律文本和风险接受取舍。

## 基线变更流程

1. 在对应基线文件登记问题 ID 和现状。
2. 说明证据、冲突、影响范围和拟变更内容。
3. 需要批准的事项取得批准。
4. 只修改唯一对应基线正文。
5. 更新 `CHANGELOG.md`，列出日期、问题 ID、文件、决定和提交。
6. 定向检查链接、编号、状态和冲突。
7. 旧文件不反向同步正文，只在来源映射登记“已由基线替代”。

## 版本冻结与切换

- 重大载体或业务边界变化必须新建明确版本基线，不得覆盖上一版本的事实和证据。
- V1.0 微信小程序版冻结后，03、04、05、12、13、14号文件仅作为V1权威归档；V2执行以15至18号文件为当前权威。
- 版本归档必须分别记录代码提交、集成分支和部署分支身份；三者不一致时不得选一个代替其余对象。
- 归档不等于删除、回滚、下线或数据清理。远程标签／分支、环境发布、数据库处理和平台配置仍按各自权限执行。

## 禁止事项

- 在其他目录创建新的执行基线或“最终版”。
- 未经核对复制旧文档结论到任务提示。
- 清理、覆盖或提交来源不明的工作区改动。
- 在文档、日志、截图或提交中保存秘密和个人敏感数据。
