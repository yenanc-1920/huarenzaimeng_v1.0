# V1 上线试运行执行规划

## 1. 规划依据与裁决顺序

本规划以 `项目管理/V1需求规格/` 为 V1 需求与 UI 的首要历史来源，其中：

1. `V1需求规格说明.md` 决定产品目标、范围、角色、逐页规格、业务规则和验收标准；
2. `前台字段与后台影响矩阵.md` 决定前后台字段、职责和联动影响；
3. `Penpot高保真源/` 的 42 个 SVG、README 和生成脚本决定已有高保真结构与文案输入；
4. 两份技术评审决定已识别的实现缺口和建议落地顺序；
5. `V1真实充值供应商技术设计.md` 决定 WINLA 接入、状态机、幂等、对账和真实验证边界；
6. 协议与隐私目录决定候选法律文本及微信隐私配置输入；
7. `开发环境故障与部署前验证基线.md` 决定外部验证不得被本地结果替代的证据边界。

当前代码、测试、事故记录和部署记录只用于确认“已经实现到哪里”和“真实运行结果如何”，不能反向删除需求。后续明确批准的架构、安全或经营决策可以覆盖历史输入，但必须在 `11-来源与历史映射.md` 和 `CHANGELOG.md` 记录来源、日期、影响项与替代关系。

## 2. 唯一目标与完成定义

当前唯一目标：在已批准 V1 范围内，将小程序、运营后台、真实数据库、微信身份、微信支付、WINLA 充值、异常恢复、运营与法律准备全部跑通，形成可观测、可暂停、可回滚的小范围生产试运行。

“全部功能跑通”必须同时满足：

- `12-V1全功能验收矩阵.md` 中全部 V1 功能达到其目标证据等级；
- P0 为 0，试运行接受的 P1 有明确责任人、期限和不阻断理由；
- 真实微信、真实数据库、真实支付、真实供应商分别有固定版本和真实环境证据；
- 正常、空、加载、不可用、可恢复失败、不可恢复失败和 UNKNOWN 等适用状态均有验证；
- 法律文本、客服路径、运营手册、监控告警、对账与回滚均就绪；
- 生产发布和真实资金验证取得南哥对固定版本、环境、金额和 RunId 的单次授权。

## 3. V1 范围归纳

### 3.1 小程序业务闭环

- 首页：今日状态、服务入口、内容入口和异常状态；
- 微信身份：协议同意、微信登录、会话恢复、退出和注销申请；
- 充值：号码输入与归一化、运营商识别、资格判断、商品目录、报价、确认、建单；
- 交易：微信支付、支付通知、供应商充值、订单列表/详情/进度、UNKNOWN 原单查询和退款状态；
- 内容：黄页列表/详情/举报，生活资讯列表/详情；
- 支持：仅使用微信官方客服入口，不接入独立二级客服案例页；
- 法律：用户协议、隐私政策及微信隐私授权配置。

### 3.2 运营后台闭环

- 管理员初始化、登录、退出、角色和字段级权限；
- 总览和异常入口；
- A100 客服案件；
- A110 交易差异与对账；
- A120 审核总队列；
- A121 黄页与城市管理；
- A122 节假日、周休与资讯管理；
- A130 供应商目录、商品、渠道、汇率、定价版本和试算；
- A140 订单、支付、充值、退款事实与脱敏详情。

### 3.3 交易与数据硬约束

- 客户端不得决定权威价格、成本、支付结果、充值结果或退款结果；
- 报价与订单冻结价格、商品、权益、号码掩码/摘要、汇率和规则版本快照；
- 支付、充值、退款、订单四条事实必须可独立追踪，不能用一个笼统状态覆盖；
- UNKNOWN 只能查询原交易，禁止自动重新扣款、重新充值、切换供应商或自动退款；
- 真实手机号只可在履约最小边界受控使用，日志、异常、审计和普通展示必须脱敏；
- 内容提交、审核、发布分别留痕；SUPER_ADMIN 的初期合并操作也不能抹去步骤审计；
- 业务图片上传不属于当前 V1；只允许产品图标、默认头像和微信授权临时头像等已批准例外。

## 5. 当前批次安排

### 批次 B0：立即执行

1. `PLAN-REQ-01`：将原需求的逐页规格、角色权限、状态合同和验收条款映射到 28 项验收矩阵；主责空空，状态 `SOURCE_AND_MAPPING_FROZEN`。
2. `OPEN-01`：在已部署固定版本上执行一次受控真实 `wx.login`；主责小测/小产，小后配合，状态 `READY_FOR_REAL_VALIDATION`。
3. `PLAN-UI-01`：建立 16 个产品业务页面、18 个当前登记路由、42 个 SVG 与后台工作区的映射，解释口径差异；主责小U/小前，状态 `MAPPING_CREATED／VISUAL_EVIDENCE_PENDING`。
4. `PLAN-GAP-01`：只登记需求—实现缺口，不立即扩展开发；主责空空/小测，状态 `IN_PROGRESS`。

### 批次 B1：OPEN-01 关闭后

并行执行 WP-03、WP-04、WP-05 的定向 DEV 旅程。每个问题只允许“定位→一次有界修复→定向验证→提交”，同一批次集中形成一个 DEV 候选，避免每个小改触发完整发布。

### 批次 B2：无资金闭环通过后

执行 WP-06。真实数据库验证需要固定数据库身份、权限、备份、迁移对象、提交和 RunId；本地 H2 或迁移脚本静态检查不能替代。

### 批次 B3：外部条件和资金授权齐备后

WP-07 与 WP-08 分别使用独立 RunId 和明确小额上限。任何支付或充值不确定结果停止自动动作，只查询原单并进入人工收敛。

### 批次 B4：候选晋级与试运行

WP-09、WP-10 完成后形成 PROD GO/NO-GO 包。只有南哥确认固定提交、试运行范围、资金上限和回滚条件后执行 WP-11。

## 6. 门禁与证据等级

| 门禁 | 必须回答的问题 | 不接受的替代证据 |
|---|---|---|
| G0 范围冻结 | 是否属于V1，来源和验收标准是什么 | 仅凭现有代码存在或个人推测 |
| G1 本地定向 | 有界改动是否通过相关测试 | 全量构建成功冒充业务通过 |
| G2 DEV业务 | 固定DEV实例是否完成真实业务行为 | Fake、H2、mock或静态路由 |
| G3 外部真实 | 微信/数据库/支付/WINLA是否返回真实结果 | 健康检查、HTTP可达或虚拟参数 |
| G4 候选晋级 | 同一提交是否通过TEST/STAGE及回滚演练 | 不同提交拼接证据 |
| G5 试运行 | 法律、运营、监控、资金和回滚是否就绪 | 仅技术测试通过 |

## 7. 发布节奏

- 定向测试用于问题闭环；完整门禁用于批次候选，不为每个小问题重复运行。
- 默认先积累一个业务域内的已验证小提交，再集中触发一次 DEV 发布。
- 外部平台构建期间只做只读监控；不因等待而重发、改配置或扩大测试。
- 发布耗时、缓存命中和镜像构建分别登记，不能用冷缓存首轮承诺后续时长。

## 8. 需要南哥介入的最小事项

仅以下事项暂停请求南哥：

1. 真实微信支付或 WINLA 充值的金额、次数与 RunId 授权；
2. PROD 发布和试运行用户范围；
3. AppSecret、支付密钥、供应商密钥等真实秘密变更；
4. 生产数据库破坏性操作；
5. 原需求与后续决策冲突且会改变产品范围、定价、法律文本或上线取舍。

其余定位、台账补全、有界开发、定向验证、普通提交及已授权分支推送，由空空按本规划继续调度。
